# Real app → static web demo: migration plan (admin side only)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring every merchant-facing screen of the real Findter app into this demo as plain HTML/CSS/JS that runs from `file://` with no server and no framework. That covers Filter, Search, every modal and shared UI piece, every Advanced Feature with its real effect, and the filter, product grid and card design editors. All data comes from fake, seeded data stored in the browser.

**Architecture:** The React source in `real-app/search-n-filter/backend/frontend` (read-only, git-ignored) is the **specification**. It is read, not copied or compiled. Each React route is rebuilt as one static page inside the demo's existing admin shell and Polaris CSS. The one new layer is a **mock API** (`assets/mock-api.js`). It answers the same `/api/...` paths the React hooks call, using seed fixtures, and persists writes to `localStorage`. That keeps the port close to one-to-one: `useAppQuery({url:'/api/filter/all'})` becomes `api.get('/api/filter/all')`, and `useFeatures().isAllowed('swatch_image')` becomes `api.features.isAllowed('swatch_image')`.

**Tech Stack:** Vanilla ES2020 (no bundler, no modules, so it works from `file://`), the existing `assets/common.css`, Node + jsdom build scripts in `tools/`, and Playwright tests in `tools/t-*.js`.

**Spec:** The real app's frontend source (`real-app/search-n-filter/backend/frontend`), its BFS file `real-app/search-n-filter/build-for-shopify.md`, this repo's `Built For Shopify.txt` and `design-rules/`.

## Scope

**In scope (the merchant admin):** Filter, Search (settings, boosters, synonyms, sort, locales, markets), Metafield, Advanced features (every feature and what it unlocks), Filter design, Product grid / card design, Year Make Model, plus every modal, banner, picker and save flow these pages use. Later and lower priority: homepage gaps, Pricing, Analytics.

**Out of scope:** Master (`pages/master/*`, `components/MasterControl/*`). The Master area already in `index.html` (Home layout, Promotion) stays exactly as it is and is not touched. **When the owner asks for a Master feature that has to connect to the app, it is added then as its own small task.** Also out of scope: the backend, App Bridge, real billing, the live Crisp chat (the current fake chat stays), storefront theme extensions, and locales other than English.

## Global Constraints

- One HTML file per page at the repo root. Sources live in `tools/build/`, and pages are generated by `node tools/build.js && node tools/build-pages.js`. Never hand-edit generated files (CLAUDE.md rule 3).
- **Scope change:** CLAUDE.md rule 4 ("first view only") and the memory `findter-replica-scope` are updated in Task 0.5 to "full admin behaviour with fake data; Master only on request".
- Nothing from `real-app/` is committed: no source files, no compiled bundles, no `.denv.env` or `.docker.env`, no real shop names or emails. Fixtures are invented (CLAUDE.md rule 5).
- Copy is English only, taken from `real-app/.../frontend/locales/en.json`.
- Every page must work at desktop width, at 768–799 px (rail) and at phone width (≤767 px), with no console errors.
- Editable pages are **draft until Save**, and leaving with unsaved changes asks first (BFS 4.1.5). This reuses the guard in `tools/build/pages.js` (`isDirty`, `askLeave`).
- `localStorage` keys use the prefix `findter.db.v1.` and every access is wrapped in try/catch. Existing keys (`findter.homeLayout.v2`, `findter.promos.v2`, the Search/Metafield keys) keep working. Search/Metafield keys are migrated into `api.db` in Phase 3.
- Run `design-rules/01-bfs-checklist.md` on every page before calling it done.

## Review Focus

1. **A feature switched off on Advanced features must lock or hide its UI everywhere.** Example: `swatch_image` off → the "Image swatch" display type is unavailable in the filter option window. Test: one Playwright step per feature in Phase 4.
2. **Reload mid-draft.** A reload shows the last *saved* state, never a half-saved draft. Test: edit, reload, the edit is gone.
3. **Cross-page data.** A metafield chosen on Metafield shows as a filter source and as a search field. A filter set's collections show in Collection booster. Test: one cross-page step per phase.
4. **Empty and limit states.** An empty shop shows the real empty states, and Free-plan limits show the real dismissible limit banners (BFS 4.3.x). Fixtures carry an `empty` variant, and the demo bar's Plan switch drives limits.
5. **Blocked storage and bad links.** In a private window, pages still render from seed data. `?id=missing` shows the real NotFound copy.

**Porting procedure (same for every page):**
1. Read the React page and its components. Write a **parity checklist** at the top of the phase plan covering every state, modal, validation message, toast, banner, empty state and feature lock, with copy taken from `en.json`.
2. List the page's `/api/*` calls. Add the routes and fixtures to the mock API, with one unit test per route.
3. Build the page with the Phase 1 kit. Where a React `<s-*>` web component has no CSS in `common.css` yet, add the matching Polaris CSS to `tools/build/pages.css`.
4. Write a Playwright test that walks the checklist at the three widths. Then run the BFS checklist.
5. Update the README page table and commit.

## Definition of done

- Every merchant route in `real-app/.../frontend/pages/` (all except `master/*`, `debug`, `ExitIframe`) has a page, or the README says why it isn't built.
- Every Advanced Feature switch has a tested effect.
- `t-mock-api.js`, `t-ui.js`, all `t-port-*.js` and the existing `t-*.js` suites pass. `t-pages.js` baselines are re-taken only for pages that were intentionally rebuilt.
- The BFS checklist has been run per page, with conflicts noted in the phase plan.
- `git status` shows nothing from `real-app/`, `tools/cap/` or `tools/profile*`.
