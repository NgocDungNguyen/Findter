# Findter Filter & Search: home screen replica

A single-file, static replica of the **Findter Filter & Search** app home screen inside the Shopify admin (desktop and mobile), plus a small "Master UI" area for arranging the homepage.

Open [`index.html`](index.html) in a browser. There is no build step and no server. It needs an internet connection for the Inter font and the app icons (loaded from Shopify's CDN).

## What's inside

- **Homepage:** onboarding guide (expand/collapse, four steps), recommended apps carousel, data insight with date picker and tooltips, app status, help & support, sync, and the Shopify admin shell (sidebar, collapsed rail, mobile drawer, search, menus, Sidekick bar).
- **Master UI** (`#/master`, via the **Master** card): tabs, and a **Home** tab where you
  - drag and drop blocks between the desktop left / right columns,
  - set a separate order for phones,
  - move the **Promotion** block (left column and phone order only). Promotions themselves are created in the **Promotion** tab of Master: a promotion goes live on the homepage as soon as it is saved, and the block shows every live promotion that targets the shop (arrows switch between them). A promotion has a name, SKU, deadline, desktop (633×160) and mobile (370×185) image, the shop types that see it, and one action: open a link (required) with an optional promo code, which is copied on the way and announced by a "Code: … copied successfully" note on the page that opens. The header **demo bar** (Store / Plan / Date / Products / Language; a "Demo data" drop-down below 1680px) fakes the shop so targeting and the **Findter app status** box can be tested. The box follows the RQM "Update: Findter Block app status" (PMS #877): Plan badge per store type (Development, Trial, Advanced trial, plan name, Free, Legacy), one date row (Expires on / Renew on / Ends on, orange at 7 days or less, month name in the chosen language), Products indexed "x / y" ("∞" without a limit; orange over the limit or while a sync runs), and the app's own limit banner for each case on top of the left column. `tools/rqm-status-shots.js` checks every case and writes numbered pictures to `RQM Images - App status/` (not committed).
- All Master changes are a **draft until you click Save**. Saved data lives in the browser's `localStorage`; nothing is sent to a server.
- Dismissing a block with its **X** only lasts until the page is reloaded.

| Search | `search.html` | "Search settings" tab, info banner, list of search fields with checkboxes. Like the app (#870), changes are saved from the black **Unsaved changes** bar at the top (Discard / Save), not a Save button. After the built-in fields there is one row (tag "Metafield") for **every text metafield chosen on the Metafield page** (Text, Text List, Multi Line Text), in that page's order. Nothing is disabled or locked. A row has the arrow to its own **Search type** (with an ⓘ tooltip for the 3 types) and **Weight** (1 to start, a bad weight blocks Save) only while **Partial search** (Advanced Search) is on **and** the row is ticked; with Partial search off no row has an arrow. The bin asks before removing; a removed metafield that is added back gets its last Search tick again. Saving a new metafield or a changed Search selection (from either page) starts an index (about 6 seconds here): a yellow "Collecting data" banner, then a green "Data indexing is completed" banner. Changes are a draft until Save, then stored in `localStorage`. **Every page with a Save button** (Search, Metafield, design pages) blocks navigation while it has unsaved changes: a sidebar item, tab or link opens "You have unsaved changes. **Design pages** (both tabs): every panel starts closed and opens from its header. A header switch (Vendor, the badges, Product card buttons) dims its whole panel while off, and each **Enable custom** switch dims its own settings; as in the app, the preview only uses a group's values while its Enable custom is on. Colors take a hex value (applied when the field loses focus, a bad value goes back) or the swatch's color picker. Save is enabled only while the settings differ from the saved ones; it stores them in `localStorage` (the real app: shop metafields) and the unsaved-changes rule below applies. "Contact us" links open the chat with the app's message.
| Pricing | `pricing.html` | current plan, product-count slider, Free / Starter plans, FAQ (static; built from the app's own page, inside this copy's sidebar) |

**Promotion image banner** (Filter and Search): one banner per page, shown on both sub tabs under the main card (the filter-set table / Collection booster block on Filter, the Search field box / Search booster block on Search). Desktop and mobile (≤ 767.98px) images come from the Shopify CDN; desktop has rounded corners, mobile does not. Each sub tab has its own bannerId (`manage-filter-set-promo`, `collection-booster-promo`, `search-settings-promo`, `search-booster-promo`). Closing it with **X** on either sub tab closes it on both, for good (stored in `localStorage`; the real app stores it on the server). Clicking the banner opens the chat and sends the merchant's message (no auto reply, at most once every 10 seconds).

Analytics is not built. It and Pricing sit in the sidebar under **View more** (the button turns into **View less**).

Promotion banners (Master → Promotion) can link to these pages with shortcuts: `/filter`, `/filter-booster`, `/search`, `/search-booster`, `/metafield`, `/ymm`, `/features`, `/design`, `/product-grid`, `/pricing`. A shortcut opens in the same tab; an `https://` link opens a new tab. With a promo code, "Code: … copied successfully" shows under the header of the page that opens (`tools/build/code-notice.js`).

The sidebar and the sub-page tabs link between all of these pages. They copy only what you see when they first open: buttons that would open settings, nested options and modals show a short "not part of this copy" message. The status toggles, the search-field checkboxes + Save, the two design pages (all settings and previews) and the phone-width table scroller do work.

All pages except `index.html` share files in `assets/`: `common.css` (all styles), `shell.js` (sidebar, menus, search overlay, Sidekick bar), `pages.js` (page behaviour) and `img/` (the app's own images). Edit a page's own markup in its `.html` file; change anything shared in `assets/`. They are generated by `node tools/build-pages.js` (run after `node tools/build.js`), so a rebuild overwrites hand edits to these files: make lasting changes in `tools/build/` instead.

## Design rules

[`design-rules/`](design-rules/README.md) lists everything to follow when designing UI/UX for the Shopify app (tokens, layout, components, tone, repo conventions) and a pre-ship checklist based on [`Built For Shopify.txt`](Built%20For%20Shopify.txt). `CLAUDE.md` makes consulting them a standing rule.

## Layout rules

- Up to 767px wide the page uses the single-column **mobile layout**, using the order from the *Mobile phone order* list. Default order: Findter app status, Sync recent updates, Onboarding guide, Help & Support, Data insight, Promotion, Recommended apps, Master. On desktop the left column is Onboarding guide, Data insight, Promotion, Recommended apps, Master and the right column is Findter app status, Help & Support, Sync recent updates.
- Every block shares one width (10px side margins) on mobile.

## Tooling

`tools/` holds the scripts used to build `index.html` (`node tools/build.js`): it flattens the app's web components to plain HTML, trims the Polaris CSS to the classes in use, and assembles the page together with the hand-written shell (`tools/build/`). The raw captures of the live admin (`tools/cap`) and local browser profiles are **not** part of the repository, so the build can't be re-run from a clean checkout. `index.html` is the deliverable.

This is an unofficial UI replica for design/prototyping. Shopify, Polaris and Findter belong to their respective owners.
